# JU Secure – Final Prototype

JU Secure is an interactive educational password-manager prototype for a university Human-Centered Design project in cybersecurity. It helps users understand password reuse, practise a clearer password-change workflow, and see how one action changes a fictional account's security status.

This final iteration preserves Emma's dark theme, magenta actions, centered mobile-width layout, navigation, account data, and working features. It builds directly on [Emma commit `af5a26b`](https://github.com/axeRob/ju-secure-emma/commit/af5a26be1cf0226e502e0cf9285559bf0e6bca7c). [Karim commit `c27236d`](https://github.com/axeRob/ju-secure-karim/commit/c27236dffba41732bf34f1aa681690423fd63555) is a reference for direct contextual actions and reduced interaction friction; its interface is not merged into Emma's design. The source repositories are preserved unchanged.

## Design rationale and user testing

The project's reported qualitative findings favour Emma's explanations and visual presentation of reused passwords, while Karim supports faster actions with less reading. The final design retains the educational strengths and brings the next action closer to the problem:

- Security shows all five actual reuse groups, with every member available for a contextual fix.
- Short risk explanations appear first. Additional education expands inline through **Why does this matter?**.
- A fix action opens an automatically generated unique password, with copy, regeneration, and one prominent **Use this password** action. Additional group context and education stay optional.
- A welcome screen provides one prominent **Get started** action into the demo vault.
- An explicit action updates the selected sample account immediately. Copying, cancelling, or leaving the screen never completes the change.
- Short success feedback puts the next account's fix first, offers a smaller return to Vault, and keeps the group comparison collapsed under **See what changed**. Overall password health remains in Vault instead of being repeated after each action.
- One discreet **Interactive prototype · Sample accounts** identification replaces repeated demo banners and lengthy interface disclaimers.

These are design responses to the supplied findings, not claims that the final iteration has been evaluated. No survey percentages, participant counts, or new research results are invented or displayed.

## Fogg Behavior Model

| Element | Interface implementation |
| --- | --- |
| Motivation | Named accounts show exactly which services share the same demo password. A concise explanation describes how an exposed password could be tried on those other services, without assuming which account matters most to the user. |
| Ability | One unique example is prepared automatically. Safe defaults, copy/reveal controls, optional regeneration, and one explicit completion action reduce decisions and unnecessary steps. Deeper explanations stay collapsed until requested. |
| Trigger / Prompt | A contextual **Fix [service] password** action sits beside the identified problem. Positive completion feedback offers the next fix as an option. Risk explanations support motivation; the action button is the prompt. |

## Demonstration workflow and boundaries

1. Enter the vault from **Get started**, then select a contextual fix in Vault, Security, or account details.
2. Review the prepared unique `DEMO-` password, copy it if desired, or generate another.
3. Choose **Use this password** to update the selected sample account. Cancellation, browser back, copying, and leaving the screen do not complete the action.
4. Read **Password updated**, then choose the next fix, return to Vault, or expand **See what changed** for the group comparison.

The interaction returns to Emma's simpler pattern, refined with direct contextual actions and user-controlled explanations. There are no external-website instruction screens or extra confirmation stages.

The app cannot change or verify passwords on external services. Its predictable generated `DEMO-` values are educational examples, not cryptographically secure passwords; **never use them on real accounts**. Real account changes require a different password generated by a trusted password manager and the service's own instructions.

All account data is fictional and held in memory. Reloading restores the initial **24 accounts: 3 safe, 15 reused, 6 weak**, default settings, and progress. There is no backend, real authentication, master-password collection, credential persistence, browser integration, synchronization, or external service integration. Import, Create vault, and Unlock are informational demo entry screens. Settings switches change demo preferences, not real locking or security services.

## Run and validate

Use Node.js **24.19.0**, pinned in `.node-version`, and npm. Work in the existing checkout; each cloud task already has an isolated environment and does not need an additional Git worktree.

```sh
cd /workspace/ju-secure-final
npm ci
npm test
npm run build
npm run dev
```

Outside the cloud environment, substitute your checkout directory. Vite binds to `0.0.0.0:5173`, serves the entry path **`/ju-secure-final/`**, and fails if the port is occupied. Open the running Vite server rather than the source `index.html`, which needs TypeScript/JSX transformation.

```sh
npm run typecheck    # TypeScript only; also included in the build
npm run preview      # Serve an existing production build
npm run test:e2e     # Playwright browser interaction tests
```

The unit tests cover account summaries, reuse normalization, resolution history, fresh demo examples, and addition/reuse behaviour. Browser tests cover the streamlined explicit-completion flow, cancellation, group display, optional explanations, retained interactions, and representative responsive layouts. Playwright is pinned to **1.58.2**. In this cloud environment, use the installed Chromium:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

For a different local or CI environment without system Chromium, install Playwright's browser first:

```sh
npx playwright install chromium
npm run test:e2e
```

For Linux CI hosts lacking browser libraries, use `npx playwright install --with-deps chromium` where system package installation is permitted. Tests and builds report their own results; this README does not assert a deployment or a fixed number of passing tests.

## GitHub Pages

The final repository is [`axeRob/ju-secure-final`](https://github.com/axeRob/ju-secure-final). Vite's production base path is **`/ju-secure-final/`**. The intended site address is **https://axerob.github.io/ju-secure-final/**; deployment must be checked after publishing before presenting this address as a live site.

In **Settings → Pages → Build and deployment → Source**, select **GitHub Actions**. Ensure GitHub Actions is enabled for the repository. No `gh-pages` branch, custom domain, committed `dist`, or routing fallback is required.

`.github/workflows/deploy-pages.yml` runs on pushes to `main` or through **Run workflow**. It installs dependencies with `npm ci`, runs unit tests, installs Playwright Chromium and its system dependencies, runs browser interaction tests, and builds the app with the pinned Node version. Only successful checks proceed to deployment of the generated `dist` artifact to the `github-pages` environment. The deployment job has Pages write and OIDC permissions.

If Pages was not configured for the first run, select **GitHub Actions** as its source and rerun **Deploy JU Secure Final Prototype to GitHub Pages**. Check the workflow's successful deployment, then open the published site and exercise its navigation. Hash routes such as `/ju-secure-final/#/learn` and `/ju-secure-final/#/vault/account/spotify` support direct reloads without server rewrites.

## Before the presentation

- Open the default welcome screen and enter the vault. Confirm **3 safe / 15 reused / 6 weak** and all five groups in Security; every group member must be selectable.
- Start Spotify's fix, generate another example, and expand the optional explanation. Copying must not complete the change. Cancel or use browser back and confirm the counts and password are unchanged.
- Complete Spotify using **Use this password**. In Vault, expect **4 / 14 / 6**; Google, Netflix, and Instagram must still share their previous password. Check the short success message, prominent next action, and optional group comparison.
- Complete Google next (**5 / 13 / 6**), then Netflix (**7 / 11 / 6**). Instagram should become safe when its last reuse relationship disappears. Other groups and weak issues must remain accurate.
- Check reveal/copy feedback, Add account's unique default and deliberate reuse confirmation, all Learn articles, Settings, and the four navigation tabs. Reload and confirm the fixtures reset.
- Check keyboard focus and mobile widths **320, 360, 390, and 430px**, plus desktop: no horizontal overflow, no phone frame, and the last account remains accessible above the bottom navigation.
- Run unit tests, browser tests, and the build; verify the published Pages site separately after deployment. Present all generated passwords and completed actions as fictional demonstrations.
